## One shape for every error

Whatever goes wrong, the body looks the same:

```json
{ "detail": "Only 253.83 is left to pay", "code": "overpayment", "balanceDue": 253.83 }
```

| Field | For |
| --- | --- |
| `code` | **Programs.** A fixed name that never changes. Switch on this |
| `detail` | **People.** A readable sentence in English. It may be reworded, so don't match on it |
| anything else | Extra facts for that error, like `balanceDue` above or `allowed` on a refused status change |

A client that shows messages in another language maps `code` to its own text. The dashboard does exactly that for English and Bangla.

The handlers that make this happen are in <Source path="app/core/exceptions.py" />. They catch the API's own errors, FastAPI's validation errors, plain HTTP errors like 404 for an unknown URL, database conflicts that slipped through, and anything unexpected, which becomes `500 internal_error` with the details in the log, not in the response.

## Status codes

| Status | Means | Example codes |
| --- | --- | --- |
| `400` | The request makes no sense as sent | `reason_required`, `unknown_foods`, `invalid_sort` |
| `401` | Not signed in, or the token is no good | `not_authenticated`, `token_expired`, `invalid_token` |
| `403` | Signed in, but not allowed | `permission_denied`, `account_disabled` |
| `404` | It doesn't exist | `not_found` |
| `409` | Allowed in general, but not in the current state | `order_closed`, `overpayment`, `table_not_available` |
| `413` | The upload is too big | `payload_too_large` |
| `422` | The body or query doesn't match the schema | `validation_error` |
| `429` | Too many requests | `rate_limited` |
| `500` | A bug | `internal_error` |
| `503` | `/health` only: the database can't be reached | |

The difference between 400 and 409 is worth a second look. **400** means "this request is wrong and always will be": a cancel without a reason. **409** means "this would be fine, but not right now": paying an order that's already paid. A client can often fix a 409 by fetching the latest state.

## Validation errors

When the JSON doesn't match the schema, the answer lists each problem with the field it belongs to:

```json
{
  "detail": "Request validation failed",
  "code": "validation_error",
  "errors": [
    { "field": "items.0.quantity", "message": "Input should be less than or equal to 100", "type": "less_than_equal" },
    { "field": "customerPhone", "message": "String should match pattern '^\\+?[0-9][0-9 -]{5,18}$'", "type": "string_pattern_mismatch" }
  ]
}
```

`field` uses the same camelCase names as the JSON, with list positions as numbers, so a form can put each message under the right input.

## Rate limits

| What | Limit | Counted per |
| --- | --- | --- |
| Signing in | 20 a minute | IP address |
| Signing in to one account | 5 in 5 minutes | Account and IP address |
| Every `/public` endpoint | 120 a minute | IP address |
| Placing or cancelling a public order | 10 in 10 minutes | IP address |
| Placing or cancelling a public booking | 10 in 10 minutes | IP address |

Past a limit, the API answers `429` with a `Retry-After` header and the same number as `retryAfter` in the body: the seconds until the next attempt is allowed.

The limiter in <Source path="app/core/ratelimit.py" /> keeps a list of recent request times per key, in memory. Two consequences:

- **With more than one instance, each counts on its own.** That's still enough to stop password guessing and order spam.
- **Restarting the API resets every count.** Handy when testing. `RATE_LIMIT_ENABLED=false` switches them off for load tests.

<Why>
  A shared store like Redis would make the limits exact across instances. For what they protect against, a rough limit per instance does the job, and it means one less service to run. If that ever stops being true, the limiter is one small class to swap.
</Why>

### Which IP address?

Behind a proxy, the connection comes from the proxy, not the visitor. The API works out the real address in this order:

1. **`CLIENT_IP_HEADER`**, if set: a header the edge proxy writes and visitors can't fake. On FastAPI Cloud that's `cf-connecting-ip`.
2. **`TRUSTED_PROXY_HOPS`**, if above 0: read `X-Forwarded-For`, counting that many proxies from the right.
3. Otherwise, the connection's own address.

<Warning>
  Set `CLIENT_IP_HEADER=cf-connecting-ip` on FastAPI Cloud. Without it, the IP comes from the first `X-Forwarded-For` entry, which anyone can set to a made-up address on every request, and the login limits stop meaning anything.
</Warning>

## Lists

Every endpoint that returns a list takes the same four query parameters:

| Parameter | Default | Example |
| --- | --- | --- |
| `page` | 1 | `?page=3` |
| `size` | 20, at most 100 | `?size=50` |
| `search` | | `?search=biryani`: case-insensitive, matches anywhere in the field |
| `sort` | Depends on the list | `?sort=-createdAt,name`: comma separated, `-` for descending |

and answers with:

```json
{ "items": [ ... ], "total": 137, "page": 3, "size": 20, "pages": 7 }
```

Each list allows sorting by a few fields; anything else is `400 invalid_sort`, with the allowed fields in `allowed`. Ties are broken by ID, so paging through a list never shows a row twice or skips one.

## Request IDs

Every response has an `X-Request-ID` header, and every log line for that request carries the same ID. Send your own `X-Request-ID` (letters, digits, `.`, `_` and `-`, up to 64 characters) and the API uses it, so one ID can follow a request from the browser into the API's logs.
